# Requirements Document

## Introduction

This specification defines a focused bugfix for the Payload 3.88.0 admin application running in Next.js 16.2.7. The admin routes currently render with missing Payload styling and invalid nested document elements because `src/app/layout.tsx` emits `<html>/<body>` around `src/app/(payload)/layout.tsx`, while Payload's `RootLayout` emits its own document. The fix adopts Next.js multiple root layouts through route groups, loads Payload's version-matched CSS, uses Payload's generated import map, and preserves the public website and admissions flow.

The scope is limited to source changes, regression tests, static diagnostics, lint/build validation, and local browser verification. It excludes deployment, commits, secret values, database credential changes, and unrelated website redesign.

## Glossary

- **Frontend_Root**: `src/app/(frontend)/layout.tsx`, the root layout for public website routes.
- **Payload_Root**: `src/app/(payload)/layout.tsx`, the root layout for Payload admin and API routes.
- **Top_Level_Layout**: `src/app/layout.tsx`, whose presence currently wraps both route groups.
- **Payload_CSS**: The version-matched stylesheet exported by `@payloadcms/next/css`.
- **Generated_Import_Map**: `src/app/(payload)/admin/importMap.js`, generated by `payload generate:importmap`.
- **Admin_Routes**: `/admin/login`, `/admin/create-first-user`, and authenticated Payload dashboard and collection views.
- **Admissions_POST**: An unauthenticated `POST /api/admissions` initiated by `src/app/(frontend)/apply/page.tsx`.
- **Document_Ownership**: The invariant that each rendered route has exactly one `<html>` and one `<body>` owner.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN `/admin/create-first-user` or another Admin_Route renders under the Top_Level_Layout THEN the response contains nested document elements and the browser reports a hydration mismatch.

1.2 WHEN Payload admin controls render without the Payload_CSS THEN inputs, selects, dropdowns, and buttons appear as unstyled native controls with broken spacing and sizing.

1.3 WHEN an admin module is resolved through `src/app/(payload)/admin/importMap.ts` THEN the application receives a manually empty import map instead of Payload's generated component map.

1.4 WHEN the public application submits `/apply` THEN `src/app/(frontend)/apply/page.tsx` sends `parentPhone`, while the `admissions` collection in `src/payload.config.ts` requires `contactNumber`, causing valid submissions to fail validation.

### Expected Behavior (Correct)

2.1 WHEN any Frontend_Root route renders THEN the route SHALL contain exactly one `<html>` element and one `<body>` element owned by `src/app/(frontend)/layout.tsx`.

2.2 WHEN any Payload_Root route renders THEN the route SHALL contain exactly one `<html>` element and one `<body>` element owned by Payload's `RootLayout`, without a wrapping Top_Level_Layout.

2.3 WHEN an Admin_Route renders THEN Payload_CSS SHALL style the admin shell, forms, selects, dropdowns, and buttons before project-specific admin overrides are applied.

2.4 WHEN Payload admin components are resolved THEN all admin consumers SHALL use the Generated_Import_Map produced by the installed Payload 3.88.0 CLI.
2.5 WHEN an unauthenticated visitor submits a complete, valid `/apply` form THEN Admissions_POST SHALL send field names matching the `admissions` collection and SHALL create the record successfully without requiring an admin session.

2.6 WHEN the browser hydrates `/admin/login`, `/admin/create-first-user`, dashboard pages, or admin collection forms THEN the console SHALL contain no nested `<html>/<body>` errors and no hydration mismatch attributable to layout composition.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN a visitor loads `/` or another public website route THEN the application SHALL CONTINUE TO apply `src/app/globals.css`, the configured Anton and Poppins font variables, the public metadata, and the shared site footer.

3.2 WHEN the application serves Payload REST or GraphQL routes under `src/app/(payload)/api` THEN it SHALL CONTINUE TO route requests through the existing Payload handlers.

3.3 WHEN an admissions payload is missing required data or contains invalid field values THEN `POST /api/admissions` SHALL CONTINUE TO return a validation failure rather than creating an invalid record.

3.4 WHEN collection operations other than the public admissions create operation are requested THEN the fix SHALL CONTINUE TO enforce the pre-fix access behavior and SHALL NOT broaden access.

3.5 WHEN custom admin styles are present in `src/app/(payload)/custom.scss` THEN they SHALL CONTINUE TO load after Payload_CSS so intentional overrides remain effective.

## Requirements

### Requirement 1: Route-Group Root-Layout Architecture

**User Story:** As an administrator, I want the Payload route group to own its document independently, so that the browser receives valid HTML and hydrates consistently.

#### Acceptance Criteria

1.1 THE implementation SHALL remove `src/app/layout.tsx` so it cannot wrap either route group.

1.2 THE `src/app/(frontend)/layout.tsx` file SHALL become the Frontend_Root and emit the public route group's `<html lang="en">` and `<body>` elements.

1.3 THE `src/app/(frontend)/layout.tsx` file SHALL retain the metadata currently exported by `src/app/layout.tsx`, the global stylesheet import, font variables, public layout classes, children, and `SiteFooter`.

1.4 THE `src/app/(payload)/layout.tsx` file SHALL remain the Payload_Root and delegate document generation to Payload's `RootLayout` without adding another `<html>`, `<head>`, or `<body>` wrapper.

1.5 THE route tree SHALL retain `src/app/(frontend)/page.tsx` as the `/` route so Next.js has a home route under one of the multiple root layouts.

1.6 THE implementation SHALL use the installed Next.js 16.2.7 multiple-root-layout convention and SHALL NOT reintroduce a shared top-level document layout.

### Requirement 2: Payload Styling and Import Map

**User Story:** As an administrator, I want the version-matched Payload assets and components to load, so that all admin controls are usable and visually correct.

#### Acceptance Criteria

2.1 THE `src/app/(payload)/layout.tsx` file SHALL import `@payloadcms/next/css` before `src/app/(payload)/custom.scss`.

2.2 THE implementation SHALL remove the manually maintained empty `src/app/(payload)/admin/importMap.ts` file.

2.3 THE `package.json` file SHALL expose a repeatable `generate:importmap` script that invokes `payload generate:importmap` from the installed Payload 3.88.0 package.

2.4 WHEN the import-map script runs THEN it SHALL generate or update `src/app/(payload)/admin/importMap.js` from `src/payload.config.ts`.

2.5 THE imports in `src/app/(payload)/layout.tsx`, `src/app/(payload)/admin/serverFunction.ts`, `src/app/(payload)/admin/[[...segments]]/page.tsx`, and `src/app/(payload)/admin/[[...segments]]/not-found.tsx` SHALL resolve to the Generated_Import_Map.

2.6 THE Generated_Import_Map SHALL contain the Payload component entries required by the current config and SHALL NOT be replaced with a hand-authored empty object.

### Requirement 3: Admin Route Rendering Regression

**User Story:** As an administrator, I want all entry and authenticated admin views to render and behave normally, so that I can create a first user, sign in, and manage content.

#### Acceptance Criteria

3.1 WHEN `/admin/login` renders THEN its form fields, buttons, spacing, and responsive layout SHALL use Payload styling.

3.2 WHEN `/admin/create-first-user` is available THEN its fields, role select, and Create button SHALL use Payload styling and remain interactable; when an existing-user state redirects this route, the redirect SHALL complete without document or hydration errors.

3.3 WHEN an authenticated dashboard or collection form renders THEN navigation, forms, dropdowns, selects, and action buttons SHALL be styled and operable.

3.4 WHEN each Admin_Route is inspected in a browser THEN the DOM SHALL contain one document root and the console SHALL contain no nested-document or layout-induced hydration errors.

### Requirement 4: Public Website Preservation

**User Story:** As a public visitor, I want the website to remain unchanged by the admin layout fix, so that existing pages and navigation continue to work.

#### Acceptance Criteria

4.1 WHEN `/`, `/apply`, `/admissions`, and at least one additional frontend content route render THEN they SHALL retain global styling, fonts, metadata, page content, and footer behavior.

4.2 WHEN navigation crosses between Frontend_Root and Payload_Root routes THEN a full-page load MAY occur as defined by Next.js multiple-root-layout behavior, but the destination SHALL render correctly.

4.3 THE fix SHALL NOT redesign or otherwise alter unrelated public components or page content.

### Requirement 5: Unauthenticated Admissions Submission Regression

**User Story:** As a prospective parent, I want to submit the public application form without an admin login, so that the school can receive my admission request.

#### Acceptance Criteria

5.1 THE request body in `src/app/(frontend)/apply/page.tsx` SHALL map `form.contactNumber` to `contactNumber`, matching `src/payload.config.ts`.

5.2 WHEN a complete valid admissions payload is posted without authentication THEN `POST /api/admissions` SHALL return a successful creation response.

5.3 IF regression testing identifies a collection access mismatch that blocks unauthenticated create THEN `src/payload.config.ts` SHALL explicitly permit only the required public create operation without broadening unrelated operations.

5.4 WHEN the endpoint returns a schema or access error THEN the test SHALL distinguish field-mapping failures from authorization failures and the implementation SHALL correct only the mismatch demonstrated by the result.

### Requirement 6: Verification Gates

**User Story:** As a maintainer, I want automated and browser-level checks, so that the rendering fix and preserved behavior are demonstrated before completion.

#### Acceptance Criteria

6.1 THE changed TypeScript, JavaScript, stylesheet, JSON, and test files SHALL have no IDE diagnostics introduced by the fix.

6.2 `npm run generate:importmap` SHALL complete and leave the generated import map current.

6.3 `npm run lint` SHALL pass.

6.4 `npm run build` SHALL pass using the existing environment configuration without changing secrets or database credentials.

6.5 Browser verification SHALL cover `/admin/login`, `/admin/create-first-user`, an authenticated dashboard, an admin collection form, dropdowns, selects, and action buttons.

6.6 Route regression verification SHALL cover `/`, `/apply`, at least one additional frontend route, `POST /api/admissions`, and the Payload REST route mount.

6.7 Verification evidence SHALL record route outcomes, visual control state, DOM document counts, console errors, and admissions response status without recording secret values or credentials.
